# Following a record from the producer to the reader

This review follows the reference [Go node](https://github.com/indexus/core/tree/5188b61) and [JavaScript SDK](https://github.com/indexus/sdk/tree/6e1bba2). The source links pin the versions examined. A house sale provides a running example. A producer can send one sale, a reader can count sales in a region, and a browser can choose which regions to draw or open next.

## Checks for this review

The two repositories contain byte-identical copies of nine binary summary fixtures and two binary record fixtures. This checks the shared examples. Independent implementations and untested inputs still require conformance testing. The SDK suite passed all 430 tests. The tree, preparation, algebra, wire, autoscale and summary Go packages also passed. A separate read with the SDK through the public Anglet gateway returned 19 sales from the record endpoint, a root total of 19, and zero unresolved prefixes in the raw root response. This is a read of one published sample.

The 2024 papers remain the historical baseline. The manifesto states the aims, the economics paper proposes a payment scheme, and the history paper records provenance. The current protocol and its empirical limits are developed in the whitepaper, client, network and properties papers.

Three boundaries deserve explicit conformance cases. The optional replication path can return local durability when a second machine has not confirmed the sequence. An IXB2 count is unsigned 32-bit per row, even when metrics are requested in binary64: the reference encoder and decoder returned zero for a synthetic row with count 4,294,967,296. This was a codec check, not a cluster load test. On the map, comparing the detailed count with the count previously announced by a parent checks coverage at a block boundary. Matching counts do not by themselves establish that the records have the same versions.
